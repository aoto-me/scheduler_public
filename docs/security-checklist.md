# ログイン処理

- [ ] パスワードを暗号化して保存しているか？

# バックエンド（PHPの場合）

### 前提

- このプロジェクトはバックエンド側でHTMLを出力しないため、基本的にバリデーションのみで、HTMLエスケープは不要

## 基本項目

- [ ] パスワードやAPIキーが露出してないか？
- [ ] パスワード、APIキーなどをソースコードに直接記述していないか？
- [ ] ログやエラーにパスワード、APIキーなどが出力されていないか？
- [ ] エラーに対してログを残しているか？
- [ ] ユーザー入力は常に不信として扱い、バリデーションしているか？
- [ ] プリペアドステートメントを一貫して使用しているか？
- [ ] CSRF対策を全ての状態変更操作に実装しているか？
- [ ] データベース接続はrootを使わず、権限を制限したユーザーとして接続しているか？（`DROP` や `ALTER` 権限は不要）
- [ ] 多層防御を行っているか？
  - ルート：CSRF + JWT + セッション一致 + デバイスID（4層）
  - ファイル配信：JWT + セッション一致（2層）
  - ZIPダウンロード：JWT + セッション一致 + デバイスID（3層）
- [ ] 最新のPHPバージョン（PHP 8.x）を使用しているか？
- [ ] エラー処理と例外管理を適切に処理し、機密情報が漏洩しないようにしているか？
- [ ] 開発環境と本番環境で異なるセキュリティ設定を使用しているか？
- [ ] Webサーバー設定でPHPファイルへの直接アクセスを制限しているか？
- [ ] OWASP Top 10 の内容に対処できているか？

## php.ini の設定

- [ ] 開発環境と本番環境で異なる設定を利用しているか？
- [ ] 本番環境ではエラー情報を表示せず、ログに記録しているか？
- [ ] リソース制限を設定しているか？
- [ ] 適切な設定をしているか？
  - [ ] `expose_php = Off` になっているか？（PHPバージョンをレスポンスヘッダーに露出しない）
  - [ ] `allow_url_include = Off` になっているか？（リモートファイルインクルード攻撃対策）
  - [ ] `enable_dl = Off` になっているか？（動的に拡張モジュールを読み込むdl()関数を無効化）

## CORS（Cross-Origin Resource Sharing）の設定

- 本番環境：
  - [ ] 不要なCORSの設定がないか？<br/>⇒ 本番環境は同一オリジン構成のためCORSヘッダー不要
- 開発環境：
  - [ ] `Access-Control-Allow-Origin` に `*`（ワイルドカード）を設定していないか？
  - [ ] 許可するオリジンを明示的に指定しているか？<br/>⇒ 開発環境は`http://localhost:5173`のみ許可
  - [ ] 認証が必要なAPIで `Access-Control-Allow-Credentials: true` を使う場合、オリジンが `*` になっていないか？

## SQLインジェクション対策

- [ ] 文字列の連結でSQLを組み立てず、プレースホルダ付きのSQL文（プリペアドステートメント）を使っているか？
- [ ] LIKE句を使う場合、`addcslashes($keyword, '%_\\')` で `%_\` をエスケープしているか？（`%` を検索すると全件ヒットするのを防ぐ）
- [ ] 入力値のバリデーションをしているか？
- [ ] データベース接続に使用するアカウントには必要な権限だけを与えているか？（`DROP` や `ALTER` 権限は不要）
- [ ] 動作確認をしたか？
  - [ ] 常に真になる：`admin' OR '1'='1`
  - [ ] データベースの内容の取得：`' UNION SELECT username, password FROM users --`
  - [ ] データの削除・改ざん：`'; DROP TABLE users; --`
  - [ ] 管理者権限の奪取：`'; UPDATE users SET role = 'admin' WHERE username = 'attacker'; --`

## OSコマンドインジェクション対策

- [ ] OSコマンドを利用していないか？<br/>⇒ コマンド実行関数の使用なし

## ディレクトリ・トラバーサル攻撃 / パス・トラバーサル攻撃 対策

- 外部からのパラメータでサーバー内のファイルやディレクトリを直接指定する実装を行う場合：
  - [ ] `..` を含むパスを拒否しているか？
  - [ ] ファイル名を `basename()` でサニタイズしているか？
  - [ ] 絶対パスと `realpath()` でパスの正規化と検証しているか？<br/>⇒ `realpath()` で正規化後、`/uploads/user{userId}/` 配下に収まっているか前方一致で確認（ファイル配信・削除・リネーム・ZIP生成の全箇所）

### 未対応・今後の検討事項

- [ ] ホワイトリスト方式で制限しているか？<br/>⇒ 現在はブラックリスト方式で制限

## ファイルインクルードの脆弱性への対策

- [ ] ユーザー入力をファイルパスに直接使用していないか？
- [ ] ホワイトリスト方式で検証しているか？

## セッション・ハイジャック / セッション固定攻撃 対策

- [ ] セッションIDをセキュリティ属性を設定した Cookie に保存しているか？
  - [ ] `session_set_cookie_params` から設定しているか？
  - [ ] `'httponly' => true` になっているか？
  - [ ] `'secure' => true` になっているか？
  - [ ] `'samesite' => 'Strict'  or 'Lax'` になっているか？
  - [ ] URLに載せる、ローカルストレージに保存する、sessionIDをJSONで返すなどを行っていないか？
  - [ ] 適切な有効期限を設定しているか？
- [ ] セッションに必要以上の機密情報を保存していないか？
- [ ] ログイン成功時に `session_regenerate_id(true)` を実行しているか？
- [ ] ログアウト時にセッションを破棄しているか？

## XSS（クロスサイトスクリプティング）対策

- [ ] ユーザーの入力に適切にバリデーションを実施しているか？
- [ ] HTTPヘッダーにContent Security Policyを設定しているか？
  - [ ] default-src 'self' になっているか？
  - [ ] style-src に unsafe-inline を許可しているか？<br/>⇒ インラインCSSのみ許可。script-src は 'self' のみで対応済みのため許容
- [ ] Cookie に HttpOnly をつけているか？

## CSRF（クロスサイトリクエストフォージェリ）対策

- [ ] トークンの検証なしで、処理を実行していないか？
- [ ] CSRFトークンを埋め込んで、サーバー側で検証しているか？
- [ ] トークンはsessionで管理し、`random_bytes()`で安全に生成しているか？
- [ ] SameSite Cookie を `Lax` または `Strict` に設定しているか？
- [ ] CORS（Access-Control-Allow-Origin）を安全に設定しているか？
- [ ] Referer制限を補助的な対策として設定しているか？（Refererは偽装可能なのであくまで補助的な対策）

## HTTPヘッダインジェクション対策

- [ ] PHPの `header()` にユーザー入力を渡す必要がある場合、入力値の検査・改行除去を行っているか？<br/>⇒ `header()` にユーザー入力を直接渡している箇所なし（`cors.php` は固定文字列のみ、`getFile.php` はサーバー側でMIMEタイプを判定、`downloadZip.php` はファイル名を `rawurlencode(basename())` でエンコード済み）

## メールヘッダインジェクション対策

- [ ] メールヘッダに改行文字が含まれないかチェックしているか？<br/>⇒ PHPMailerが内部で処理するため不要
- [ ] ユーザー入力を直接ヘッダに渡していないか？
- [ ] `filter_var(..., FILTER_VALIDATE_EMAIL)`でバリデーションを行っているか？
- [ ] 外部ライブラリ（PHPMailer など）を使っているか？

## クリックジャッキング対策

- [ ] X-Frame-Options ヘッダを設定しているか？<br/>⇒ `frame-ancestors 'none'` でカバーしているため、省略
- [ ] Content-Security-Policyで frame-ancestors を設定しているか？
- [ ] （フレームを使う必要がある場合）許可するドメインを明示的に制限しているか？

## バッファオーバーフロー対策

- [ ] ユーザー入力の長さに制限を設けているか？
- [ ] PHPの`post_max_size`や`max_input_vars`などの設定を適切に行っているか？
- [ ] 必要に応じてファイルアップロードサイズを制限しているか？

## DoS（サービス妨害）対策

- [ ] N+1クエリになっていないか？
- [ ] 処理のタイムアウトが設定されているか？<br/>⇒ 通常処理は `max_execution_time = 300` が適用され、OGP・RSS取得のみ別途設定あり。現状、個別のタイムアウトの設定が不要と考えているが、問題があれば追加を検討
- [ ] 外部URLへ `file_get_contents` / `curl` でリクエストする場合、タイムアウトとレスポンスサイズ上限を設定しているか？<br/>⇒ OGP：タイムアウト10秒・2MB制限、RSS：タイムアウト10秒・5MB制限を設定済み

### 未対応・今後の検討事項

- [ ] APIごとにレート制限があるか？<br/>⇒ ログイン処理とAIへのリクエスト以外にレートなし。限られたユーザーしか利用してない都合で、現状不要と考えているが、問題があれば追加を検討

## SSRF（サーバーサイドリクエストフォージェリ）対策

- 外部URLへ `file_get_contents` / `curl` でリクエストする場合：
  - [ ] リクエスト前にホストを解決し、プライベートIP（`127.x`・`10.x`・`192.168.x` 等）をブロックしているか？
  - [ ] リダイレクト自動追跡を無効化し、転送先URLも同様に再検証してから追跡しているか？

## 認可制御の欠如への対策

### アクセス制御

- [ ] 認証（ログイン確認）と認可（権限チェック）を区別して実装しているか？
- [ ] APIごとに認可チェックが必ず入っているか？
- [ ] ユーザーIDはサーバー側で決定し、リクエストから受け取っていないか？
- [ ] 他人のIDを指定してもデータを取得・更新できないか？（IDOR対策）

### データ制御

- [ ] リクエストのフィールドを個別に取り出してDBに渡しているか？（`$_POST` をそのまま渡していないか）
- [ ] レスポンスで不要なカラムを返していないか？（必要なカラムのみ SELECT しているか）

## エラー情報の露出

- [ ] 開発環境と本番環境で異なるエラー設定を使用しているか？
- [ ] 本番環境でエラー発生時にAPIやDB情報がユーザーに見えないか？
- [ ] 本番環境でエラー発生時にスタックトレースがユーザーから見えないか？
- [ ] ユーザー向けのエラーメッセージの設計しているか？
- [ ] エラーに対してログを残しているか？
- [ ] ログに個人情報・トークン・パスワードが含まれていないか？
- [ ] ログへのアクセス権限が制限されているか？
